# 产物合同

## 目标

生成一份同时包含 PRD 与 Tech Spec 的 Markdown 文档。产品行为合同是需求定义的单一权威位置；技术部分通过 `BEH-*` 引用行为，不复制另一套需求。

## 文档状态

只使用以下 `status`：

- `draft`：存在会改变任一 `BEH-*`、验收条件、范围边界或技术映射的未决项，或完成一致性关卡与最终规格审查所需的证据仍然缺失。
- `review`：一致性关卡与最终规格审查全部通过；剩余未知不会改变产品合同或技术方向，等待用户校准当前版本。
- `approved`：用户已经明确确认当前版本。

新生成的规格不能自行进入 `approved`。实质修订改变任一 `BEH-*`、验收条件、范围边界或技术映射时，一致性关卡与最终规格审查通过后进入 `review`，否则进入 `draft`。只有用户看到并明确确认当前版本时才能进入 `approved`。文档状态不表示下游任务、实现、发布或合并是否可以开始。

## 版本与路径

- 新规格默认使用 `version: 0.1`。
- 修订既有规格时遵守文件已有版本约定；没有约定时只在用户确认版本策略后修改版本号。
- 创建目标必须位于 `docs/specs/`。
- 用户当前消息明确指定 `docs/specs/` 内的路径时，创建模式使用该路径。
- 显式路径越界：
  - 处理：保持工作区不变。
  - 输出：只要求用户提供 `docs/specs/` 内的路径。
  - 禁止：静默改用默认路径。
- 用户当前消息未指定路径时，创建模式写入 `docs/specs/<date>-<spec-name>.md`。
- 创建模式的 `date` 使用用户当前消息明确指定的产物日期；未指定时使用执行环境的当前日期，格式为 `YYYY-MM-DD`。
- 修订模式保持目标文件的现有路径和文件名日期；当前日期不改变修订目标。
- `spec-name` 优先使用用户给出的规格名称；否则从已确认目标生成简短标题。保留 Unicode 字母和数字，将空白与路径分隔符替换为 `-`，移除会产生隐藏文件、父目录跳转或无效文件名的字符。
- 规范化后的名称不得是 `AGENTS`、`CLAUDE`、`SKILL`、`README`、`CONTRIBUTING` 等可能被工具解释为指令、入口或项目约定的保留名称。命中保留名称时，从已确认产品目标生成描述性名称；无法安全确定时停止并请求确认。

### 修订目标解析

仅在用户明确要求修订、替换或覆盖既有规格时，按以下顺序确定目标：

1. 使用当前用户明确给出的路径；目标不存在时停止，不按该路径创建新规格。
2. 用户指向“刚才”“上次”或“这个”规格，且当前会话只产生了一份与当前目标匹配的规格时，使用该文件。
3. 否则检查 `docs/specs/`；文件标题或文件名与当前产品目标匹配时，将其列为候选。
4. 只有一个候选时使用该文件；没有候选时只询问目标路径；存在多个候选时列出路径并只要求选择一次。

禁止用文件日期、版本号、修改时间或目录顺序猜测多个候选中的权威文件。解析完成后先读取目标完整内容，再建立修订候选稿。

### 写入授权门

写入前按顺序检查：

1. 模式门：讨论模式停止在对话输出；创建或修订模式继续。
2. 目标门：创建模式按“版本与路径”确定安全目标；修订模式只使用“修订目标解析”得到的现有文件。
3. 操作门：创建目标必须不存在；修订目标必须存在，且当前用户已明确授权修订、替换或覆盖。
4. 范围门：创建目标符合“版本与路径”的目录和保留名称规则。
5. 快照门：实际写入前目标与检查时快照一致。

任一门失败时保持目标不变。工具写入失败时在对话返回完整规格，并报告文件未写入。

## 文档骨架

每份规格使用同一骨架，不设置“精简”或“完整”模板：

```markdown
# <规格名称>

- status: draft | review | approved
- version: <版本>
```

骨架之后由 Agent 从下列顶层章节目录中按需组合。章节名称是封闭集合，必须使用表中原名并保持相对顺序；不得自创同义顶层标题。章节内部的小节、表格和表达形式由当前内容决定。

| 顺序 | 顶层章节     | 选择条件                                                                               |
| ---- | ------------ | -------------------------------------------------------------------------------------- |
| 1    | 背景与目标   | 存在多主体、业务压力、阶段目标或非目标，无法由 `BEH-*` 直接且无损地表达                |
| 2    | 产品行为合同 | 始终保留；定义唯一的 `BEH-*` 行为、触发条件、可观察结果、验收条件和状态                |
| 3    | 产品边界     | 存在跨多个 `BEH-*` 的权限、信任、异常输入或范围约束，放入单条行为会重复或隐藏影响      |
| 4    | 技术基线     | 多个 checkout 事实或材料冲突共同改变技术设计或验证；单一事实写入技术设计即可           |
| 5    | 技术设计     | 始终保留；承载 `BEH-*` 的实现映射及适用的状态、接口、失败和运行边界                    |
| 6    | 验收与验证   | 始终保留；定义宿主无关的可执行验证、通过证据、完成条件和失败处理                       |
| 7    | 决策记录     | 命中 `SKILL.md` 的决策记录条件；只引用影响位置，不复述产品行为、技术证据或形成过程     |
| 8    | 未决事项     | 未知、待验证或待裁决会改变 `BEH-*`、验收、技术方向或一致性关卡；一般性缺资料不单独成章 |
| 9    | 参考资料     | 正文实际引用外部文档、正式材料或相关规格；无此类引用时省略                             |

产品行为合同默认使用下列字段；仅当等价表达更适合当前规格时才改变呈现形式，不得丢失字段语义：

| ID  | 触发与前置条件 | 可观察行为 | 验收条件 | 状态 |
| --- | -------------- | ---------- | -------- | ---- |

每个可选章节只有在选择条件成立，而且删除后会丢失独立决策信息时才出现。适用风险必须写入职责对应的章节；不适用内容直接省略，不用空章节、“不适用”占位或重复已有合同。

### 执行与验证合同

每份规格必须在“验收与验证”中提供以下宿主无关合同，使人工、agent 或 CI 都能据此执行和判断完成：

- 为每项验证分配稳定 `VER-*`，并记录覆盖对象、前置条件、执行或检查、通过证据和证明边界。覆盖对象引用一个或多个 `BEH-*`、保持边界或不可接受结果；证明边界说明该验证不能证明什么。
- 命令、脚本、文件和观测入口必须来自当前 checkout 或明确材料。无法确认时保留“待验证”和最小定位动作，不补造可执行入口。
- 明确哪些 `VER-*` 是完成目标所必需的；条件性验证必须写明触发条件，不能因当前环境不可用而静默降级为可选。

每份规格必须在完成条件前记录：`相关修改` 指改变任一 `VER-*` 的覆盖对象、技术承载、前置条件、执行或检查、通过证据的变更。

完成条件只有在以下检查全部通过时成立：

- 所有目标行为、保持边界和不可接受结果都有验证覆盖。
- 全部必需 `VER-*` 在最后一次相关修改后重新通过。
- 规格标记为需要直接检查的产物均已检查。
- 不存在阻塞未决项。
- 最终变更没有超出规格边界。

规格还必须遵守以下执行边界：

- 未运行、无法运行或只有推测结果的验证必须保留为未验证或阻塞，不得视为通过。规格的 `status` 不表示当前 checkout 已经通过执行前核对。
- 记录执行前需要重新核对的规格版本、阻塞未决项、关键技术证据、依赖或配置，以及与目标重叠的工作区改动；规格生成时不得把未来核对写成已通过。
- 记录与当前任务有关的失败分流、修复后的重验范围和阻塞停止条件。具体判断遵守 `evidence-and-consistency.md` 的“执行与验证证据”。

`VER-*` 使用 `VER-001` 形式，并在同一规格内保持稳定。修订时保留仍有效标识；删除验证时不重用旧编号表达另一项验证。简单规格可以用紧凑表格或短列表表达，但不得丢失上述字段语义。

## 信息归属

每项信息只在一个权威位置定义：

| 信息                                   | 唯一归属                            |
| -------------------------------------- | ----------------------------------- |
| 可观察产品行为                         | 产品行为合同中的稳定 `BEH-*`        |
| 跨多个 `BEH-*` 的权限、信任或范围约束  | 产品边界                            |
| 共同改变技术设计或验证的 checkout 事实 | 技术基线                            |
| 实现承载                               | 技术设计，并引用 `BEH-*` 或保持边界 |
| 可执行验证、通过证据和完成条件         | 验收与验证                          |
| 已实际发生的选择及理由                 | 决策记录                            |
| 未知、待验证、待裁决和冲突             | 未决事项                            |
| 正文引用的外部文档、正式材料或相关规格 | 参考资料中的稳定 `REF-*`            |

- 已归属信息在其他章节只引用，不换一种措辞重新定义。
- 技术基线使用短列表，只保留会改变技术设计或验证方式的事实。路径、版本和日期仅在缺少它们会改变事实解释时记录；只有单一事实时把它写入技术设计并省略技术基线。
- 技术取证、设计或验证出现未被 `BEH-*` 覆盖的主体、权限、范围、可观察结果或不可逆后果时，停止受影响的技术设计；现有证据足以修正时返回产品合同，仍需选择时按未决项影响分级请求用户裁决，不得写成技术假设。

## 正文风格

- 每个章节先写结论，再写约束和证据；一段只表达一个判断，细节较多时使用短列表。
- 表格只承载字段固定、内容短小且需要横向比较的数据。技术设计需要长说明时，按 `BEH-*` 或组件使用小节展开。
- 事实和依据紧邻对应结论，避免让读者跨章节拼接同一判断。
- 已由产品行为合同定义的行为只引用 `BEH-*`，不换用另一套措辞重复解释。
- 删除背景复述、过程旁白和没有决策信息的内容。

## 字段规则

- 章节内部只保留与当前规格有关的内容；必需但没有依据的内容标记为“未知”“待验证”或“待裁决”。
- `BEH-*` 使用 `BEH-001` 形式，并在同一规格内保持稳定。修订时保留仍有效标识；删除行为时在决策记录说明，不重用旧编号表达新行为。
- 产品合同记录非目标、必须保持的行为、权限边界和不可接受结果。
- 产品合同区分一次性实验、阶段性范围和长期产品规则。
- 成功标准描述主体、行为、关系或环境的可观察变化，不把上线或使用次数单独当作成功。
- Tech Spec 通过映射表引用 `BEH-*`。产品行为的措辞只在产品行为合同中修改。
- 每项决策保留“选择、状态、理由、影响”四个语义字段。“选择”只写机制或取舍的短标签，不得包含条件、数值或完整行为结果；“影响”只引用受影响的 `BEH-*`、技术设计或验证。行为细节和技术映射留在各自权威位置，不在决策记录复述。
- 决策状态只使用“已确认”“暂定”“被拒绝”或“被替代”。用户当前明确采纳的选择标记为“已确认”；材料中的选择保留原状态，直到用户明确确认。
- 事实证据、Agent 假设、待验证事实和待裁决问题分别留在技术基线、技术设计、验收与验证或未决事项，不得包装成决定。决定依赖未来读者需要独立定位的外部文档、正式材料或相关规格时，在理由中引用对应 `REF-*`。
- 未决事项是未知、待验证、待裁决和冲突的唯一汇总位置；已经在产品行为合同或技术设计表达的状态不重复记录。
- 会影响后续执行的未决事项必须额外记录以下字段：

  | 字段     | 允许值                                           |
  | -------- | ------------------------------------------------ |
  | 阻塞范围 | 目标定义、实现、验证、发布、不阻塞               |
  | 解除权威 | 用户裁决、仓库证据、外部事实、环境恢复、权限批准 |
  | 执行处理 | 自主调查、继续不受影响部分、暂停                 |

## 参考资料

- 仅登记正文实际引用、且未来读者需要独立定位的外部文档、正式材料或相关规格。材料是否由本次任务提供不改变其角色：只描述目标或变更的 brief、requirements、change 等工作输入，以及当前规格自身或写入前快照，不登记；承载版本化 API、平台、标准或其他外部事实的材料按正式资料登记。
- 正文使用资料的结论必须显式引用对应 `REF-*`，例如“该对象签名仅适用于 SDK 3.x（REF-001）”；文件名、路径或链接不能替代该标识。
- 每项使用 `REF-001` 形式的稳定标识，只声明一次，并记录名称、位置，以及会影响解释的版本或日期。
- 不生成统一来源清单或 `sources` 元数据。用户决定保留在产品合同或决策记录；checkout 路径和代码证据按信息规模保留在技术基线或技术设计；命令、通过条件和执行结果保留在验收与验证。不得把这些内容复制进“参考资料”。
- 不存在符合条件的资料时省略整个章节，不生成空表、占位符或孤立 `REF-*`。
