# 实现与验证

本阶段由原 implementation terminal 按任务账本完成实现、相关提交、必需验证和证据回写。

## 1. 实现与提交

- 按账本中的 `dependsOn` 选择可执行的 `IMP-*`。运行时计划只镜像当前任务，任务身份、状态和依赖以账本为准。
- 每个提交依次执行：实现、相关验证、自查 diff、修复、复验、commit。
- 提交后立即在对应 IMP 中记录 commit 和已取得的验证证据。
- 实现提交与相关检查完成后标记 `implemented`，允许下游 IMP 开始。全量验证或 Review 尚未齐全时不得标记 `done`。
- Spec 在执行中发生变化时停止受影响任务并报告宿主。返回准备阶段重新对账并通过 `check --ready` 后才能继续。
- 完成当前 dispatch 后发送一次 `worker_done`。宿主处理结果后，通过原 implementation terminal 派发下一阶段。
- 禁止跳过有效测试。

## 2. 验证场景预检

完成全部实现后，运行所有必需 `VER-*` 和 `AGENTS.md` 规定的适用检查。

非确定性、live、并发或故障注入场景执行前，在当前任务或验证证据中记录：

- 对应 VER；
- 目标阶段；
- 进入条件；
- 注入条件；
- 预期终态；
- 清理方式。

无法证明系统能够进入目标阶段，或注入条件会在目标阶段之前被消费时，不得执行该验证场景。

## 3. 处理重复验证

- **可恢复 pending**：外部状态仍可能自然推进，且当前合同允许有界恢复时，保留原任务并执行下一次有界观察。
- **新证据重试**：下一次尝试引入新的判别变量、触发条件或证据来源时，允许重试。
- **停止**：当前合同不允许继续有界观察，且没有新的判别证据时，停止重试并报告。

## 4. 持久化证据

- `/tmp` 只保存可重建缓存。
- 不可重建的输入、归档包、清单、外部对象 ID 和验证报告保存在 worktree、session root 或已提交证据中。
- 验证默认由原 implementation terminal 执行并同步写入账本。
- 验证委派给其他 thread 时，宿主在进入下一阶段前把结果交回原 implementation terminal。
- 原 implementation terminal 完成委派证据的回写和提交后，宿主才能继续。
- 验证失败时，由原 implementation terminal 修复、重验并 commit，并同步更新受影响 IMP 的状态与证据。

## 5. 收口外部资源

每个验证创建的外部资源归入一种状态：

- **已完成**：关闭运行资源并保留必要证据。
- **可恢复 pending**：记录负责人、恢复入口和保留原因。
- **已被替代**：关闭旧资源并记录替代对象。

最终交付前，关闭不再需要的 task、browser、PID、容器和 named session。除用户明确要求继续监控的任务外，不得遗留没有负责人和恢复入口的活动资源。

## 6. 阶段完成条件

- 所有必需验证在最后一次相关代码修改后通过；
- 所有通过结论都有实际执行证据；
- 委派证据已回写并提交；
- 验证资源已归类；
- 受影响 IMP 已达到与现有证据一致的状态。
