# 实现与验证

本阶段由实施者在一个连续 dispatch 内按任务账本完成实现、相关提交、必需验证和证据回写，直到到达 decision boundary。

## 1. 实现与提交

- 按账本中的 `dependsOn` 连续选择可执行的 `IMP-*`。运行时计划只镜像当前任务，任务身份、状态和依赖以账本为准。
- 每个提交依次执行：实现、相关验证、自查 diff、修复、复验、commit。
- 提交后立即在对应 IMP 中记录已取得的验证证据，不记录 Git revision。
- 一个 dispatch 连续处理所有可执行 IMP，直到遇到产品决策、Spec 变化、需协调员执行的外部验证、阻塞 finding 或其他明确 decision boundary；禁止为每个 IMP 单独派发或提前结束。
- 实现已提交到 task branch 且相关检查完成后标记 `implemented`，允许下游 IMP 开始；全量验证和 Review 齐全后标记 `done`。
- 实施中需要更新 Spec 时，实施者停止受影响任务，提交已经完成且验证过的改动，并向协调员交回 clean task worktree。协调员按 `prepare-and-dispatch.md` 第 3 节更新 Spec 和账本；Child Gate 再次放行后，原 implementation terminal 继续实施。
- 遇到无法从当前 Spec 或已确认页面合同判定的事项时，实施者向协调员报告未知项及影响面；协调员选择继续、更新 Spec、执行 Spike 或请求产品决策。
- 到达停止条件或完成条件后发送一次 `worker_done`。协调员处理结果后，向实施者派发下一阶段。

## 2. 验证场景预检

完成全部实现后，运行所有必需 `VER-*` 和 `AGENTS.md` 规定的适用检查。

非确定性、live、并发或故障注入场景执行前，在当前任务或验证证据中记录：

- 对应 VER；
- 目标阶段；
- 进入条件；
- 注入条件；
- 预期终态；
- 清理方式。

无法证明系统能够进入目标阶段，或注入条件会在目标阶段之前被消费时，不得执行该验证场景。

## 3. 处理重复验证

- **可恢复 pending**：外部状态仍可能自然推进，且当前合同允许有界恢复时，保留原任务并执行下一次有界观察。
- **新证据重试**：下一次尝试引入新的判别变量、触发条件或证据来源时，允许重试。
- **停止**：当前合同不允许继续有界观察，且没有新的判别证据时，停止重试并报告。

## 4. 持久化证据

- `/tmp` 只保存可重建缓存。
- 不可重建的输入、归档包、清单、外部对象 ID 和验证报告保存在 worktree、session root 或已提交证据中。
- 验证默认由实施者执行并同步写入账本。
- 验证委派给其他 thread 时，协调员在进入下一阶段前把结果交回实施者。
- 实施者完成委派证据的回写和提交后，协调员才能继续。
- 验证失败时，由实施者修复、重验并 commit，并同步更新受影响 IMP 的状态与证据。

## 5. 收口外部资源

每个验证创建的外部资源归入一种状态：

- **已完成**：关闭运行资源并保留必要证据。
- **可恢复 pending**：记录负责人、恢复入口和保留原因。
- **已被替代**：关闭旧资源并记录替代对象。

最终交付前，关闭不再需要的 task、browser、PID、容器和 named session。除用户明确要求继续监控的任务外，不得遗留没有负责人和恢复入口的活动资源。

## 6. 实施者验证完成条件

- 所有必需验证在最后一次相关代码修改后通过；
- 所有通过结论都有实际执行证据；
- 委派证据已回写并提交；
- 验证资源已归类；
- 受影响 IMP 已达到与现有证据一致的状态；
- 未知项已报告协调员并明确路由（继续 / Spike / 产品决策），没有未经授权的 Spike、Spec 或 ADR 修改。

实施者达到本节条件后发送 `worker_done`。协调员随后进入 Review 与集成阶段，检查当前目标分支并确定最终 integration candidate；协调员独立验证不在本阶段替代实施者验证。
